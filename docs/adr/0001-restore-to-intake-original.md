# 还原永远回到初始原件;裁剪共享备份且不进历史

Eddy 的压缩与裁剪都是原地覆盖的破坏性操作,需要一张安全网。我们决定:文件第一次被破坏性操作前,其精确字节保存为一份备份(初始原件),存于 `~/Library/Application Support/Eddy/originals/`;「还原」一律用初始原件原子覆盖当前文件(含重建被格式转换删除的原文件、删除转换产物),然后删除历史条目、备份和主窗口行——不检测文件是否被外部修改过,不提供分步撤销。裁剪不产生历史条目、不计入节省统计,只共享(或在纯裁剪时创建)同一份备份;因此纯裁剪文件的还原窗口只到 app 下次启动(启动时清理无历史条目引用的孤儿备份)。

## Considered Options

- **逐操作 undo 栈**(压缩→裁剪→裁剪各存一档,可逐步回退):被否——与 app "一步操作"哲学冲突,备份体积成倍增长,心智模型复杂。
- **还原前检测外部修改并弹确认**:被否——用户明确要求还原就是对称的覆盖,零弹窗。
- **裁剪也进历史(标记类型、豁免统计)**:被否——历史的语义保持"成功的压缩替换"单一含义。

## Consequences

- 备份磁盘占用无硬上限(≤ 500 份初始原件),由历史 500 条上限间接封顶;条目删除/淘汰/清空时同步删除备份。
- 压缩后又裁剪的文件,一次还原直接回到压缩前的初始原件,不存在"回到裁剪前"的中间态。
- 功能上线前的旧历史条目没有备份字段,不提供还原入口。
- 裁剪动画 GIF 目前经 ImageIO 重编码(时序完整保留,体积偏大);待自研 GIF 引擎(见 `docs/specs/gif-support.md`)落地后应切换到它。
